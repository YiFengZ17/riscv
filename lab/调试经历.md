# 调试经历记录

本文根据本次实验过程和个人回顾整理，作为实验报告“总结”部分的素材。具体错误截图、调试时的寄存器数值和修复后的运行结果，应与实际保存的记录对应；本文中的算例用于解释原理。

## 1. 加法：不知道如何判断溢出和传递进位

最初实现加法时，我不清楚如何处理无符号整数溢出，认为两个非负数相加，结果不应该小于原来的操作数，因此难以理解通过比较结果与操作数来判断进位（carry）的方法。

通过查阅和分析算例，我了解到固定宽度的无符号运算会按模回绕（wraparound）。例如，32 位无符号数 `0xffffffff + 1` 的数学结果是 `0x1_00000000`，但保存的低 32 位为 `0`，此时结果小于原来的操作数，说明产生了进位。

多字加法还需要区分两步：先计算 `A[i] + B[i]`，再加上上一字传来的进位。两步都可能溢出，因此必须分别检查，任意一步产生进位，就向高一字传递 `1`。我也曾先更新 `carry` 再把它加入本字，导致旧进位被覆盖；修复时调整了更新顺序。

这一过程让我理解了：本字保存的是低 32 位结果，超出的部分通过单独的进位变量传递，最后一次进位表示整个 1024 位加法是否溢出。

## 2. 减法：借位方向与本位不够减

最初我按照纸上竖式的直觉，尝试在本位不够减时，通过循环向高位寻找可以借位的位置，再修改中间各位。这种方法使控制流程复杂，而且会修改输入数组，不符合实验要求。

通过查阅，我了解到无符号减法下溢（unsigned subtraction underflow）同样会回绕。例如，32 位的 `0 - 1` 会保存为 `0xffffffff`，等价于本字加上一个基数 `2^32` 后再减。因此，无需真的修改高位输入来“借到”这个基数，只需记录高一字之后应扣掉的借位（borrow）。

在从低字向高字处理时，传入的 `borrow` 表示低一字向当前字借走了 `1`，所以当前字要再减去它；更新后的 `borrow` 则表示当前字是否需要向高一字借 `1`。这里借位的来源始终是高位，只是扣减动作延迟到下一轮执行。

实现时分别检查 `A[i] - B[i]` 是否借位，以及再减旧借位是否产生新的借位。最终借位为 `1` 表示整个数满足 `A < B`；输出数组已经是模 `2^1024` 的差值，无需再整体加一或修改输入。

## 3. 乘法：累加宽度、整体移位和取位操作

乘法中，我起初没有充分区分输入和乘积的宽度：输入是 32 个 32 位字，完整乘积是 64 个 32 位字，即 2048 位，而不是“64 位”。因此，固定只处理 32 个字的 `add1024` 不能直接用于完整乘积的累加，否则高半部分和跨边界进位得不到处理。

后来我将同样的进位逻辑扩展到 64 个字，并在每次开始累加时将进位初始化为零。

移位方面，我曾把数组元素整体挪动一格，误以为这相当于左移一位。实际上，一个元素保存 32 位，移动一个元素相当于乘以 `2^32`。正确做法是每个字左移一位，并把低一字的最高位接到本字最低位：

```c
T[j] = (T[j] << 1) | (T[j-1] >> 31);
```

这一步需要从高字向低字执行，以免覆盖还未读取的数据，最低字再单独左移。我也曾把移位放在处理乘数位的循环之外，导致工作数组没有随每一轮翻倍，后来将其移回循环内部。

取出乘数某一位时，我曾混淆移位方向和位编号。通过查阅明确：第 `k` 位位于 `B[k/32]`，字内编号为 `k%32`，应右移到最低位，再与 `1u` 做按位与（bitwise AND）：

```c
(B[k / 32] >> (k % 32)) & 1u
```

位编号从零开始，所以 `k=31` 对应 `B[0]` 的最高位。取位使用右移，生成乘法部分积（partial product）则让工作数组整体左移，两者用途不同。

## 4. 除法：余数 R 的移位和新位引入

实现二进制长除法（binary long division）时，我对余数 `R` 的移位处理也存在困惑。每轮不是单独修改某一个数组元素，而是把整个余数左移一位，再将被除数当前处理的位放入最低位，对应 `R = 2R + 当前位`。

通过查阅并结合竖式推演，我明确了处理顺序：从被除数的最高位向最低位依次取位；先按高字到低字的顺序完成余数的跨字移位，再更新最低字并引入当前位；随后比较余数与除数，够减时减一次并设置相应商位。

调试过程中，还出现过从高字比较时用 `>=` 提前退出的问题。两个高字相等不能说明整个数的大小，应继续比较低字；只有遇到不相等的字才能决定大小，全部相等时才确定需要相减。设置商位时也应使用无符号常量 `1u`，避免 C 中把有符号的 `1` 左移到第 31 位所带来的问题。

这一过程让我把移位操作和长除法的循环不变量（loop invariant）联系起来：每轮结束时余数满足 `R < B`，因此下一轮落位后最多减一次除数即可。

## 5. 汇编移植：对齐、打印、全局数组与栈空间

从 C 移植到汇编时，我发现 C 中由编译器处理的细节都需要显式安排，包括地址对齐（alignment）、字符串表示、多分支控制流程、数组地址以及栈帧（stack frame）的分配与恢复。

最初我不清楚怎样表达打印字符串、多个测试用例和全局数组，也不确定乘除法需要多少工作内存，容易在返回时忘记恢复已经分配的栈空间。通过查阅并对照当前实现，我逐步明确了以下做法：

- **对齐：** 32 位字的首地址应按 4 字节对齐，RARS 中可用 `.align 2`；调用前栈指针需保持 16 字节对齐。当前程序在主入口对齐 `sp`，各运算函数分配的栈帧大小也都是 16 的整数倍。
- **字符串和打印：** 使用 `.asciz` 定义以零结尾的字符串，使用 `la` 取得地址；RARS 字符串打印使用 `a7=4`，十六进制字打印使用 `a7=34`。打印放在主程序或独立辅助函数中，算术核心不调用 `ecall`。
- **多个测试用例：** C 的 `switch/case` 可改成标签、条件分支和跳转，主程序用循环依次选择测试数据。
- **全局数组：** 使用标签和 `.space` 分配空间，通过 `la` 取得首地址。第 `i` 个字的地址是基址加 `4*i`，不能把元素编号直接当成字节偏移。
- **乘法工作空间：** `T[64]` 需要 256 字节，再加上保存寄存器及对齐空间，当前乘法栈帧共 272 字节。
- **除法工作空间：** 临时差值 `D[32]` 需要 128 字节，再加上保存寄存器、返回地址（return address）和对齐空间，当前除法栈帧共 160 字节。
- **函数返回：** 使用过的保存寄存器（callee-saved register）要恢复；除法调用减法，还需保护 `ra`。必须先从栈中恢复寄存器，再把 `sp` 加回相同的分配量，确保返回时与入口一致。

通过这些调试，我认识到，汇编移植不仅是把 C 运算换成指令，还需要明确每个值的位置、每块内存的范围，以及函数调用前后哪些状态必须保持不变。
